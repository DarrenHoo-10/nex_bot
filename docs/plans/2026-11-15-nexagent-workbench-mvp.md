# NexAgent 会话工作台 MVP 实施方案

首批交付 **Web、Windows 桌面端 × Codex、Claude Code、ZCode**。用户能从 NexAgent 接续自己在原生 App 或 CLI 已经打开的会话，查看历史、发送、排队、引导、编辑后再次发送，也能停止当前运行。Windows 同时承担设备执行器和桌面客户端两种角色，两者分别验收。交互以[工作台定稿](../design/nexagent-workbench-v1.md)为基线，底层沿用[已有 Agent 模式](2026-11-15-agent-mode-implementation.md)。

## 1. 用户怎样操作

| 场景 | Web 与 Windows 的一致行为 | 成功依据 |
| --- | --- | --- |
| 空闲时发送 | Enter 发送，Shift+Enter 换行。发送中保留消息与投递状态。 | 对应原生会话接收消息，两端都出现同一轮回复。 |
| 运行中继续输入 | 默认动作是「排队」。队列紧贴输入框，显示内容、顺序、编辑和撤回。等待审批也视为占用。原窗口先开启新轮次时继续等待。 | 条目已由 Core 持久化才显示已排队。上轮结束后按序逐条发送，每次等待上一条对应轮次结束。 |
| 引导当前任务 | 输入后选择「引导」即可向正在执行的轮次补充要求。已排队的消息也可点「立即引导」。 | 原生运行端确认引导被目标轮次接受。若轮次已结束，保留文字并允许用户选择排队或重新发送；从队列转引导失败且确定未投递时恢复原位置。 |
| 编辑已发消息 | 自己的消息旁提供「编辑并重发」，键盘聚焦或鼠标悬停可见。在输入框载入原文和仍可用的附件，支持取消并恢复原草稿。空闲时直接重发，运行中可选择排队或引导。缺失附件在提交前可移除或补选。 | 在同一会话产生一条关联原消息的新消息，保留原文和已有回复。重复点击一次提交只产生一条。排队中尚未投递的消息则直接编辑原条目，位置保持。 |
| 停止当前会话运行 | 有正在执行的轮次时，输入框显示独立的方形「停止」按钮，排队和引导入口仍可用。点击立即显示「正在停止」，暂停本会话队列。 | 设备确认该轮次已结束后恢复普通输入，可在同一会话继续说话。保留已生成文本、附件和排队项，有待发项时提供「继续队列」。用户在原窗口停止同样需要刷新状态。 |
| 设备离线或结果不确定 | 已排队内容重开可见。发送、引导或停止结果无法核实时显示「待确认」。操作能力随连接恢复重新探测。 | 重连从原会话对账。不能确认是否执行的命令不自动重投，停止超时也不提前消费队列。 |

“编辑并重发”在 MVP 中采用追加修订语义。它适用于有稳定消息 ID 的本人原生历史消息及由 NexAgent 投递的消息。停止的作用域为当前会话的当前轮次，随后仍可接续原上下文。单独运行的后台任务按它们自己的生命周期更新。

## 2. 三个 Harness 的接入顺序与扩展点

第一批设备端调查同时覆盖三家。每家分别从原生 App、独立 CLI 开始，记录软件版本、启动方式、原生会话 ID、可用通道及结果。Claude 桌面范围限定为 Code 会话。新建托管会话与接续外部现有会话分别标记来源。

| Harness | 从项目已有代码起步 | 首次必须拿到的证据 |
| --- | --- | --- |
| Codex | [App 数据库发现](../../server/personal-os/cli-agents-node/codex-app-db.ts)、[共享 daemon](../../server/personal-os/cli-agents-node/codex-daemon.ts) | App 与 CLI 各起一个原生 thread，分别核实可写通道、原窗口回显、定向引导和定向中断。数据库发现成功只计入读取。 |
| Claude Code | [会话发现](../../server/personal-os/cli-agents-node/discovery.ts)、[本地 inbox](../../server/personal-os/cli-agents-node/inbox.ts) | 在 Windows 验证两个入口各自可用的授权通道。分别记录 inbox 已写入、原会话接收、当前轮次接受引导、中断生效四种结果。仅有文件记录或发送回执时保留相应限制。 |
| ZCode | 当前 [共享协议](../../shared/cli-agents.ts) 与 [SQLite 约束](../../server/personal-os/cli-agents/schema.ts) 只接受前两家。新增设备适配器。 | 第一阶段先验证授权连接既有 Host、定位已有 conversation、订阅原生事件与提交命令，再用独立 CLI 重做。记录实际版本可用的引导和中断接口。接入前提与上游链接见[技术方案第 2 节](../design/nexagent-workbench-v1.md)。 |

**扩展边界。** 在设备端 [bridge](../../server/personal-os/cli-agents-node/bridge.ts) 和 [discovery](../../server/personal-os/cli-agents-node/discovery.ts) 后提取编译期注册的 Harness 适配器。每个适配器提供稳定 ID、发现与读历史、当前会话能力探测、发送、引导、停止和原生事件归一化。启动、续接、fork、归档、删除、模型及技能按能力实现。适配器负责把事件关联到原生会话、轮次和消息，Core 统一负责鉴权、队列、修订关系与重复请求处理。UI 根据会话能力与运行状态渲染，品牌文字和图标从展示注册表读取。

第四个 Harness 的接入工作应限于注册 ID、实现适配器、补图标和适配器契约用例；队列状态机、消息组件和导航树可以复用。SQLite 的 engine 列从固定双值 CHECK 迁移为可扩展的 Harness ID，允许写入的 ID 仍由协议注册表校验。旧设备沿用现有协议；Core 针对旧客户端过滤其无法解析的 engine，快照与增量采用相同过滤逻辑。新工作台只对 Web 和 Windows 启用，共享 Web 包在其他宿主保持既有入口。

## 3. 命令与存储

复用 [Core 路由](../../server/personal-os/cli-agents/routes.ts)、[hub](../../server/personal-os/cli-agents/hub.ts)、[设备流](../../server/personal-os/cli-agents/stream.ts) 和已有会话、操作、消息表。下面是待实现契约。操作归属校验沿用现有账号及设备边界。

| 命令 | 请求与前置条件 | 写入及返回 |
| --- | --- | --- |
| 发送／排队／引导 | 扩展 `POST /api/cli-agents/send`，携带 sessionKey、requestId、clientMessageId、delivery（send / queue / steer）、正文和附件引用。引导必带 expectedTurnId。 | 接收时返回 messageId、operationId、状态、版本。只有 queue 可等待下一轮。send 与设备实际状态冲突时返回 busy 或 turn_changed，由用户选择下一步。 |
| 编辑并重发 | 同一发送契约，新的 clientMessageId 和 requestId，另带 revisesMessageId。校验原消息归属、作者与附件授权。 | 按新消息正常投递，记录原消息引用；同一修订提交重试沿用原 requestId。 |
| 编辑／撤回／转引导 | 新增会话内队列条目命令，携带条目 ID、期望版本、requestId；转引导另带 expectedTurnId。 | 仅 queued 状态可原子改写、撤回或认领用于引导；已被消费者认领则返回最新状态，供用户选择编辑后重发。 |
| 停止／继续队列 | 扩展现有 `POST /api/cli-agents/interrupt`，携带 expectedTurnId、requestId；另加显式继续队列命令。 | Core 先登记停止请求并暂停消费，设备核对轮次后执行。迟到中断不得命中新轮；重新打开会话或设备重连都保留暂停状态。 |

**持久化最小集。** 在设备原生会话 key 之上保存逻辑会话、父 ID、类型和版本。增加 outbox 记录，包括会话、递增队列序号、clientMessageId、requestId、正文与附件引用、修订源消息 ID、目标轮次、投递状态及版本。每个会话保存队列暂停原因与消费租约。按账号和逻辑会话约束消息标识唯一，按账号约束 requestId 唯一，同键异参返回冲突。敏感正文沿用项目加密存储约定。协议日志只留关联 ID、状态和错误码。

**并发与恢复。** 发送和引导经“待投递 → 已认领 → 已确认 / 明确失败 / 待确认”流转，撤回是队列条目的终态。Core 在事务内认领队首，设备派发前再次检查会话、预期轮次及可写性。原生接口需要具备等效的定向或原子条件保证才可启用相应操作。设备回执和原生转录通过原生消息 ID 或操作关联去重。Core 崩溃或确认丢失时，先读取设备操作记录和原生快照；仅在有幂等保证或能证明从未投递时重发。两条正文相同的独立消息必须保留。遇到不确定的队首，后续排队项等待对账。

正常完成时消费下一条；本端或原窗口主动停止时暂停消费。停止和引导并发时按同一会话串行执行，已受理停止后拒绝新的同轮引导并保留草稿。设备迟到的旧轮次事件按轮次标识合并。每次更新通过现有推送同步 Web 与 Windows，掉线客户端先取快照再接增量。

## 4. 可独立合并的工作包

| 包 | 依赖 | 改动位置和交付物 | 合并时的验收 |
| --- | --- | --- | --- |
| P0 原生通道验证 | 无 | Windows 隔离账号、临时工作目录，按第 2 节建立三家 × 两个入口的实测表。风险最大的 ZCode 和外部会话停止从第一天查。 | 每行都有版本、复现步骤、证据和限制。没有授权写通道的入口单列阻塞项。 |
| P1 协议与存储 | 可与 P0 并行 | shared 协议、schema、Core hub。迁移旧 CHECK，保留原会话、items、索引和外键；建立关系、outbox、能力快照及操作版本。 | 从包含两家历史和消息的旧库升级，核对行数、引用及旧端快照解析；新增 ZCode 可以写入，再接一项测试用适配器可复用同一套契约。 |
| P2–P4 三个设备适配器 | P0 对应入口、P1 | P2 Codex、P3 Claude Code、P4 ZCode，各自独立提交。建立按会话与版本的发送／引导／中断路由、能力快照和事件映射。 | 每家跑相同契约测试，再分别提交 App、CLI 的原窗口往返及轮次控制证据。外部 route 的中断需有原生路径，当前 bridge 的中断只走托管终端地址。 |
| P5 消息调度 | P1，可用模拟适配器先行 | Core routes、hub、设备 bridge。实现四种用户动作、消费暂停、回执恢复、跨端事件和幂等。 | 两个客户端同时改队首、双击重发、断线丢回执、Core 重启、轮次更替及停止竞态均有自动化断言。 |
| P6 对话输入与消息操作 | P5 契约 | [输入框](../../src/personal/cli-agents/Composer.tsx)、[消息列表](../../src/personal/cli-agents/TranscriptView.tsx)、api 与 stream。将预览内存队列切到真实状态；实现第 1 节交互和键盘操作。 | Web 排队，Windows 修改后从原窗口看到修订内容。编辑后取消恢复原草稿，两端只显示同一条投递结果；等待停止时输入内容保留。 |
| P7 工作台接正式数据 | P1、对应适配器 | [会话树](../../src/personal/cli-agents/SessionList.tsx)、[工作区](../../src/personal/cli-agents/CliAgentsWorkspace.tsx)、新建会话、Git 卡片与右栏。按定稿接改名、fork、worktree、选区侧聊、注释和中文阅读；能力及活动来自设备。 | fork 首帧即在父项下，子会话可 fork 一次；真实上下文继承有独立用例。已托管 PTY 从右侧直接输入；外部原生会话必须独立探测 PTY。正式入口断开夹具后仍可用。 |
| P8 双端发布候选验收 | P2–P7 | 使用新的隔离 Core、Windows 设备执行器、浏览器及实际 Windows 客户端。证据按第 5 节整理。 | 通过两端 × 三个 Harness × App / CLI 的矩阵，逐项标明限制和阻塞。升级与关闭新入口后旧功能可用。 |

首个可演示切片是 **一个已在 Windows 原生窗口聊到一半的 Codex 会话，在 Web 续聊，Windows 工作台同步看到结果**。随后用同一入口验收排队、编辑重发、引导和停止，再用 Claude Code、ZCode 逐项复测。这一里程碑与三家全部达标分别记录。

## 5. 测试与放行

每次使用[项目隔离验证流程](../verification/README.md)。用临时仓库、独立测试账号和独立原生配置目录，不接管用户正在工作的窗口。每次保存版本、输入动作、原生会话与轮次的脱敏关联、双端回显及断线恢复结果。

| 用例 | 操作 | 判定 |
| --- | --- | --- |
| N1 原会话接续 | 在原 App / CLI 发 A，NexAgent 发一个依赖 A 才能回答的 B，回到原客户端查看 C，再重连。 | 原生 ID 全程一致，两端均显示 B、C，重连没有第二条 B。 |
| N2 队列与编辑 | 运行时 Web 排 B、C，Windows 把 B 改成 B2，关闭一个客户端再重启 Core。 | 原轮正常结束后只收到 B2，然后 C。加入相同正文的两次独立提交能分别送达。 |
| N3 引导 | 长轮次运行时直接引导一次，再把排队项转引导；分别注入刚好结束和正在审批的情况。 | 成功时原轮次接收，中间不会多起一轮；期限冲突和缺少能力时可恢复文字。 |
| N4 编辑重发 | 对已完成的用户消息改文后重发，模拟双击及确认包丢失，并在另一端重开。 | 原文和原回复仍在，新增一条修订消息及其后续结果，双端一致。 |
| N5 停止及继续 | 排队两条后停止，分别从 Web、Windows、原窗口触发；让旧停止回执在下一轮开始后到达。 | 当前轮次终止，后续轮次未受影响，队列保留且暂停。可发送新消息或手动继续队列。 |
| N6 失败恢复 | 设备断开、旧设备不认识新 engine、已发现但不可写、只有未确认回执、双客户端并发操作。 | 不误报成功、不重复执行，其他兼容会话仍能使用。 |
| N7 工作台回归 | 定稿导航、选区侧聊、可删除注释、默认中文、Git 活动卡及可控 PTY；分别在浏览器和 Windows 壳操作。 | 交互与定稿一致。Windows 验证从 Core 加载和随包 UI 两条路径，以及恢复连接后的真实输入回显。 |

N1–N5 按三家、两个原生入口、两个 NexAgent 客户端逐格记录，列出“通过 / 受限 / 未通过”及理由。只读、仅托管成功、缺少引导或停止的入口均作为具体缺口展示，保留在三家 MVP 验收清单内。某一入口只有供应方客户端可用而不能被 NexAgent 授权接续时，记录协议阻塞与复测条件，交付结论必须注明该缺口。

现有回归入口如下。第一条验证已存在的适配链路；第二条验证组件；第三条开启可交互的隔离原型。原生控制证据需由 N1–N5 另行取得。

```powershell
corepack pnpm exec vitest run server/personal-os/cli-agents-node/bridge-outside.test.ts server/personal-os/cli-agents-node/inbox.test.ts server/personal-os/cli-agents-node/codex-daemon.test.ts
corepack pnpm exec vitest run src/personal/cli-agents
node scripts/smoke-cli-agents.mjs --workbench --serve=18809
```

交付时在 `docs/verification/` 保存实测矩阵，附版本和复现命令。先部署兼容读取的 Core，再升级 Windows 设备执行器，最后按宿主、Harness 和已验证的会话能力开放 UI。回退时暂停新命令消费、保留队列及投递记录，已派发操作先对账。移动端和 macOS 原生客户端的交互适配留在后续版本。
