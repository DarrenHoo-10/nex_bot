# 记忆重新设计：核心记忆 + 按提示召回

状态：草案（2026-10-28）。范围：Core（`server/personal-os`）；设置页增加“记忆检索”配置（Web 与 Mac/iOS）。
与 [压缩时机方案](compaction-timing.md) 独立，可并行。

## 1. 目标

- 每次任务开始时，**只按用户这次的提示召回相关记忆**，不相关的不进上下文。
- 始终加载的只有一份**小而稳定的核心记忆**，放在可缓存的前缀里。
- 其余记忆留在库里，模型需要时用工具检索。
- 记忆维护有成本上限，失败有退避，不再出现死循环。

## 2. 参考：Claude 的做法

| 层 | Claude | 本方案对应 |
|---|---|---|
| 始终加载 | Claude Code 每次会话加载 `CLAUDE.md` 和记忆索引 `MEMORY.md`（每条一行的索引，内容在单独文件里）；claude.ai 加载一份定期合成的记忆摘要 | 核心记忆：身份与长期偏好 + 一行一条的主题索引，有硬上限 |
| 按需读取 | 索引里的条目需要时才打开对应文件；claude.ai 用 `conversation_search` / `recent_chats` 工具检索过去的对话 | `memory.search` / `memory.read` / 原文检索，模型自己决定何时查 |
| 写入 | 用户说“记住…”或模型判断有长期价值时写；先查重，有则更新、错了就删 | 显式写入 + 后台提取，统一去重与更新 |

关键点：Claude 不会在每次请求里塞入大量历史记忆，而是**小索引常驻、细节按需取**。

## 3. 现状问题（代码 + Tokyo 线上只读数据）

每次模型请求时进入上下文的记忆相关内容：

| 内容 | 位置 | 问题 |
|---|---|---|
| 记忆文档账本：最近 15 篇、最多 12,000 字 | `memory.ts` `prompt()`，在稳定前缀 | 不看相关性，按更新时间全塞 |
| 长期记忆召回：最多 12 条 / 2000 Token | `runtime.ts:471` | **每次模型请求都召回**（含工具续写）；查询词是“该助手最近 4 条消息（跨所有会话）+ 当前输入”，不是用户这次的提示 |
| “理解”文档（偏好/决定/经验） | `assistant-memory.ts` `recall()` | 相关性为 0 也强制带上 |
| 其他会话最近消息：2000 Token | `agents.ts` `context()` `otherRecentWork` | 与当前任务无关也带上 |
| “之前/上次”关键词触发的原文召回：2500 Token | `agents.ts` `context()` | 靠关键词猜，命中粗糙 |
| 相关段落档案：1500 Token | `agents.ts` `context()` | 与上面的召回各自为政，查询词不同 |
| 工作笔记 | `agents.ts` `context()` | 合理，保留 |

线上发现的严重问题（0.9.17 发版后约 11 小时）：

- 助手“私人秘书”的“理解”任务调用 **310 次、约 585 万 Token**，其中只有 63 次模型正常返回，
  且**一份理解文档都没有写成**（全库 `kind='understanding'` 为 0 行）。
- 原因：`profile_at` 只在写入成功后更新，失败后 30–60 秒又满足触发条件，形成重试循环；该助手的
  每日记忆预算被设成 1,000 万，预算也没拦住。其他 4 个助手已提示“今日记忆维护预算已用完”。
- 记忆文档账本（`memory_documents`）在所有助手上都是 0 篇；事实/经验/观察共约 190 条，集中在“私人秘书”。

## 4. 新设计

### 4.1 三层

```text
┌ 稳定前缀 ─────────────────────────────────────────────┐
│ 核心记忆（≤ 1500 Token，变化少，可缓存）               │
├ 易变尾部（每个任务开始时一次）────────────────────────┤
│ 按本次提示召回的相关记忆（≤ 2000 Token，可为空）       │
│ 工作笔记（当前会话，≤ 1000 Token）                    │
└───────────────────────────────────────────────────────┘
库里（不进上下文）：主题条目、原子事实、段落档案、对话原文
→ 模型用 memory.search / memory.read / entry: / episode: 按需取
```

每次请求中记忆相关部分的上限：核心记忆 1500（可缓存）+ 召回 2000 + 工作笔记 1000 = **4500 Token**。
现状上限约为：记忆文档 18,000 + 召回 2000 + 其他会话 2000 + 原文召回 2500 + 段落 1500 + 工作笔记 9000
≈ **35,000 Token**，且每次工具续写都重新计算。

### 4.2 核心记忆（替代“理解”文档和账本）

- 每个助手一份，表 `assistant_core_memory(bot_id, content, version, updated_at)`；工作区共享一份
  （`scope='workspace'`），两者都放进稳定前缀。
- 内容固定两部分：
  1. **关于用户的长期事实与偏好**：称呼、语言、常用设备、明确的长期规则（如“部署前不用再问”）。
  2. **主题索引**：每条一行，`- 标题 — 一句话 (memory:<id>)`，指向库里的详细记忆，像 `MEMORY.md`。
- 硬上限 1500 Token；超过时合并或移除最旧、最少被召回的索引行。
- 更新方式是**增量补丁**（新增/修改/删除某几行），不是每次整体重写。
- 来源：
  - 用户明确说“记住…/以后…/不要再…”时，模型调用 `memory.core.update` 立即写入（先读当前版本）。
  - 后台整理：新观察累计 ≥ 5 条且距上次更新 ≥ 6 小时，才生成一次补丁。
- 用户可在设置里查看和编辑（复用现有记忆页，不新增说明文字）。

### 4.3 按提示召回

- **时机**：每个任务第一次模型请求前召回一次，结果在本任务内复用；工具续写不再重新召回。
- **查询**：只用本次用户输入（含附件名），去掉“最近 4 条消息”。
- **候选池**统一为一个：事实、经验、观察、段落档案、记忆文档。替代现在三套各自的召回
  （`recall`、`recalledHistory`、`relatedEpisodes`）。
- **检索**：见 4.7 混合召回（BM25 + 向量 + 重排）；有相关性门槛，低于门槛的不要；
  命中为 0 时**什么都不注入**。
- **预算**：只按 Token 限制，不限条数，不提供配置。每条带 `memory:<id>` 或 `episode:<id>`，模型可展开原文。
  - 召回总预算 **2000 Token**；单条最多 400 Token，超出部分截断并标注“原文见 <引用>”。
  - 段落档案只放简报（`brief`，≤ 300 Token），全文用 `episode:<id>` 展开。
  - 依据（Tokyo 2026-10-28 实测，估算 Token）：事实中位 88、经验中位 120、观察中位 258（p90 537）；
    2000 Token 约可容纳 6–10 条典型记忆，或 4 条长观察。常见小窗口 128k 下不到 2%，
    每个任务只付一次（不进缓存前缀），与现状单次上限持平。
  - 预算不用满：相关性门槛决定放什么，预算只防宽泛查询一次拉入大量边缘内容。
- 删除：`otherRecentWork`、关键词触发的 `recalledHistory`、“理解”文档强制注入、记忆文档账本全量注入。

### 4.4 工作笔记

**现状**：每个助手一份（`assistant_working_notes` 主键是 `bot_id`），同一助手的所有会话共用；
三个写入入口（模型 `memory.write(scope="context")`、压缩时 Core 写入、段落归档）都截到 6000 字，
约 9000 Token，每次请求都在易变尾部全价计费。

**新规则**

- **按会话存**：新表 `conversation_working_notes(conversation_id, bot_id, content, task_id, version, updated_at)`，
  主键 `conversation_id`。只放进本会话的请求；跨会话的长期信息交给核心记忆和召回。
- **上限 1000 Token**（按估算计算）。内容限定为：当前目标、有效约束与决定（含原因）、未完成事项、
  待回答问题、关键引用。
- **超出上限不截断**：
  - 模型写入超过 1000 Token → 拒绝并返回“工作笔记超过 1000 Token，请精简后重写”，由模型自己精简；
  - Core 在压缩或归档时生成的笔记超过上限 → 用整理模型压到 800 Token 以内再写入；
    压缩失败则保留旧笔记，不写入半截的内容。
- 压缩与归档的指令中给出上限，要求输出不超过 800 Token。
- 会话开启新段落时保留笔记中仍有效的约束和未完成事项，其余由段落档案承接（现有逻辑）。
- 遗忘（forget）与删除会话时一并删除该会话的工作笔记。

### 4.5 记忆的组织：主题条目 + 原子事实

**现状**：记忆分散在 5 个各自独立的存储（记忆文档、自动记忆、“理解”文档、工作笔记、段落档案）。
线上只有自动记忆有数据（约 190 条），其中大量是助手某次说了什么、做了什么（进程号、某张截图），
是一次性过程细节；每条孤立，同一件事被拆成多条，召回时互相抢预算。

**新结构**（合并为一套，层级对应 Claude 的 `MEMORY.md` 索引 + 主题文件）：

```text
核心记忆（每次加载）
  └─ 主题索引：每个主题一行 → memory:<topic-id>
主题条目（召回/检索的主要单位）
  └─ 原子事实（证据，带原文引用与哈希）
段落档案（一段对话的记录，可检索）
对话原文（entry: / message:）
```

- **主题条目**（`assistant_memories.kind='topic'`，取代 `observation` 与 `understanding`）：
  - 一个主题一条，如“部署流程”“设备与网络”“沟通偏好”“nex_bot 项目”；标题 + 正文（≤ 400 Token，
    与单条召回上限一致）+ 证据列表（原子事实 id）。
  - 新事实写入时先按向量与标题找最接近的主题：相似度达到门槛就更新该主题（增量改写正文），
    否则新建主题。不再做“事实 → 观察 → 理解”的多层重写。
  - 主题正文超过 400 Token 时拆分为子主题，或淘汰被新事实取代的旧内容。
  - 主题变化后，核心记忆的主题索引行同步更新（增量补丁）。
- **原子事实**（保留 `fact` / `experience`）：只作证据，不单独进入召回；主题不存在时暂时可被召回。
- **记忆文档**（`memory_documents`）：用户或模型主动写的长文保留，参与召回；不再每次全量注入。

**提取规则收紧**（`retain` 指令）：

- **记**：关于用户的长期信息（身份、偏好、习惯、长期规则）；项目与环境的稳定事实（项目、服务器、
  设备、账号结构、约定）；用户做出的决定及原因；反复出现的问题与解决方法。
- **不记**：助手的自述与过程汇报；一次性细节（进程号、临时路径、某次报错全文）；从原文或段落档案
  就能查到的内容；密码、密钥等敏感信息（现有过滤保留）。
- 拿不准时不记；用户明确要求“记住”的一定记。

### 4.6 按需检索

- 保留 `memory.search`（文本、`entry:`、`message:`、`episode:`）、`memory.read`、`memory.write`、
  `memory.delete`、`memory.forget`。
- 新增 `memory.core.update(patch, expectedVersion)`。
- 系统提示加一句：需要过去的信息、用户提到“之前/上次”时，先用 `memory.search` 查，不要猜。

### 4.7 混合召回：BM25 + 向量 + 重排

**现状**：只有词法一路，且较粗糙。

- 长期记忆与段落档案用 FTS5 取 100 条候选后，丢掉 BM25 分数，改用自写打分（`search-terms.ts`
  `relevance`：只看中文 2 字片段是否出现，无词频、无稀有度、无长度归一）。
- FTS5 用 `unicode61` 分词，把连续汉字当成一个词，与查询侧的 2 字片段不一致。
- 记忆文档和历史原文是整句 `LIKE '%…%'` 子串匹配。
- 向量检索只在旧的 Hindsight 模式里有，线上开启个人记忆的助手不走那里。

**新方案**（写入与查询都在 Core，不依赖 Hindsight 服务）：

1. **BM25（词法）**：索引改用 FTS5 `trigram` 分词（中英文、代码标识一致切分），按 FTS5
   `bm25()` 排序，取前 50。记忆文档与历史原文也纳入同一种索引。不足 3 个字符的查询词退回前缀匹配。
2. **向量（语义）**：写入时生成 embedding，存入新表
   `memory_vectors(kind, ref_id, model, dims, vector BLOB, content_hash)`；查询时余弦相似度取前 50。
   单助手记忆在千条量级，内存暴力计算即可（1024 维 × 几千条为毫秒级）。
3. **融合**：两路用 RRF（k = 60）合并，去重后取前 20。
4. **重排**：用 reranker 对前 20 条与用户输入重新打分，低于门槛（初始 0.3，按线上数据调）的丢弃；
   再按 2000 Token 预算截断（见 4.3）。
5. **精确标识**：查询含 `entry:` / `message:` / `episode:` / `memory:` 时直接查，不走上述流程。

**服务（沿用 Tokyo Hindsight 的配置，已在 2026-10-28 从 Tokyo 实测）**：

| 用途 | 服务 | 模型 | 实测 |
|---|---|---|---|
| embedding | SiliconFlow（OpenAI 兼容 `/v1/embeddings`） | `Qwen/Qwen3-Embedding-8B`，1024 维 | 200；热请求 0.5–1.3 秒；“部署 Core 到东京服务器”与“上线 Tokyo”相似度 0.71，与“今天天气”0.46 |
| rerank | SiliconFlow `/v1/rerank` | `Qwen/Qwen3-Reranker-8B` | 200；约 2.1–2.8 秒；相关文档 0.70，无关文档 0 |

- `Qwen3-Reranker-4B` 在该账号下已停用，`bge-reranker-v2-m3` 不存在。
- Hindsight 当前的 reranker 指向局域网 TEI（`jiayu-desktop`，`bge-reranker-v2-m3`）。服务本身可用，
  但 Hindsight 一次送过去的候选太多，超过 TEI 的单次上限（`max_client_batch_size=32`、
  `max_batch_tokens=16384`），近 3 天 1351 次全部是 `413 Request Entity Too Large`。Core 不依赖它。

**配置：可配置，未配置时走默认**

embedding 和 rerank 各自独立配置，放在模型设置里的“记忆检索”一组：

| 项 | embedding | rerank |
|---|---|---|
| 协议 | OpenAI 兼容 `/embeddings` | `cohere`（`/rerank`，`query` + `documents`，SiliconFlow / Jina / Cohere 通用）或 `tei`（`/rerank`，`query` + `texts`） |
| 地址 | `base URL` | `base URL` |
| 模型 | 模型名 | 模型名（TEI 可为空） |
| 维度 | 可选（模型支持时传 `dimensions`） | — |
| API Key | 可选 | 可选 |
| 开关 | 开 / 关 | 开 / 关 |

解析顺序（每项独立）：

1. **用户在设置里配了** → 用用户的。Key 与模型 Key 一样加密存入 `secrets`，接口与日志不返回明文。
2. **没配** → 用服务端默认：`/etc/nexbot/core.env` 里的 `NEX_EMBEDDINGS_BASE_URL/MODEL/DIMENSIONS/API_KEY`
   与 `NEX_RERANK_FORMAT/BASE_URL/MODEL/API_KEY`。生产默认设为 SiliconFlow `Qwen3-Embedding-8B`（1024 维）和
   `Qwen3-Reranker-8B`；Key 在服务器上从 `/data/hindsight/.env` 复制，不经过本机、不进仓库。
3. **服务端也没有默认**（自建、本地开发）→ 该项关闭：没有 embedding 就只用 BM25，没有 rerank 就用 RRF。

其他规则：

- 设置页显示当前实际生效的来源：“自定义”“默认”或“未启用”；默认时只显示模型名，不显示地址和 Key。
- 保存时发一次测试请求（embedding 算 1 条、rerank 排 2 条），失败则不保存并显示报错。
- 改变 embedding 的模型或维度后，旧向量停止参与召回，在后台按新配置重建；重建完成前由 BM25 覆盖。
- rerank 每次最多发 20 条候选，每条截到 512 Token，保证在 TEI 这类自建服务的单次上限内。
- Web 与 Mac/iOS 设置页同时增加该分组（仅标签和输入框）；Android 无模型设置页，不涉及。
- 合成环境与测试使用本地假服务，不调用 SiliconFlow。

**时延与降级**

- 每个任务只召回一次（见 4.3），引入的时延约为 1 次 embedding + 1 次 rerank，约 2–4 秒。
  召回与 worker 启动并行，总超时 4 秒；超时或报错时：
  - 向量不可用 → 只用 BM25；
  - rerank 不可用 → 用 RRF 排名，预算降到 1000 Token（没有重排时排名较不可靠，少放一些）；
  - 全部不可用 → 不注入召回记忆，任务照常进行。
- 查询为寒暄、诸如“好的”“继续”等短句（去除标点后 < 4 个字符）时跳过召回。
- 写入侧 embedding 在记忆维护后台生成；尚未生成向量的条目仍可被 BM25 召回。
  迁移时为现有约 190 条记忆和段落档案补生成向量。
- 这部分 Token 很少（embedding 每条几十 Token），计入 `assistant_usage`，`purpose='embed'` / `'rerank'`。

**遗忘与一致性**

- 记忆或来源被删除、更新、遗忘时，同一事务内删除对应向量与索引行；`content_hash` 不一致的向量不参与召回。
- 更换 embedding 模型或维度时，旧向量按 `model` / `dims` 过滤并在后台重建。

### 4.8 记忆写入提示词的 Token 区间

Token 为 Core 估算值（中文约 1.5/字）。线上校准显示真实值约为估算的 0.56–1.08 倍
（glm 0.56、grok 0.80、claude-sonnet-5-5 1.08，2026-10-28 实测）。

**现状**（每次模型请求，含工具续写）

| 部分 | 下限 | 上限 | 线上实测（0.9.17 之后） |
|---|---:|---:|---|
| 记忆文档账本（前缀） | 0 | 约 18,000 | 所有助手 0 |
| 长期记忆召回 | 0 | 2000 | 平均每次请求：私人秘书 1911（16 次全是这个值）；开发专家中位 1197、p90 1746 |
| 其他会话最近消息 | 0 | 2000 | 有其他会话的助手均在 1890–1990，几乎顺着上限 |
| 历史原文召回 | 0 | 2500 | 只在出现引用或“之前/上次”时 |
| 段落档案 | 0 | 1500 | 线上只有 2 份 |
| 工作笔记 | 0 | 约 9000 | 183–766 |
| **合计** | **0** | **约 35,000** | 典型约 **2,600–4,700**，每次工具续写重算 |

**新设计**

| 部分 | 位置 | 下限 | 典型 | 上限 | 计费 |
|---|---|---:|---:|---:|---|
| 核心记忆（个人 + 工作区共享） | 稳定前缀 | 0 | 400–900 | 1500 | 缓存命中时约 0.1 倍 |

## 7. 验证

隔离 Core、合成模型、真实 worker：

- 无关提示：易变尾部不含任何召回记忆；相关提示：只含相关条目，且不超过 2000 Token、单条不超过 400 Token。
- 一个任务内多次工具续写：只召回一次，结果一致。
- 核心记忆在稳定前缀中，多轮请求前缀逐字节不变；更新后只变一次。
- 用户说“记住我叫…”：核心记忆立即更新；下一个任务可见。
- 维护失败：退避生效，调用次数有上限；预算硬顶生效。
- 遗忘（forget）同时清理核心记忆中引用了被遗忘来源的索引行。
- 工作笔记：两个会话互不可见；模型写入超过 1000 Token 被拒绝并提示精简；Core 生成的超长笔记被压缩而非截断。
- 提取：助手自述、进程号一类的内容不生成记忆；同一主题的新事实更新已有主题，不新建重复条目。
- Token：每次请求中记忆部分不超过 4,500，短句输入时只含核心记忆与工作笔记。
- 现有记忆相关测试全部通过（更新依赖旧注入方式的用例）。

上线后观察：每次请求中记忆部分的 Token 数、召回命中条数与为 0 的比例、`memory.search` 调用次数、
记忆维护每日 Token 与失败次数。

## 8. 取舍

- 召回依赖外部 SiliconFlow 服务；不可用时退回 BM25，召回质量下降但任务不受影响。
- 每个任务开始增加约 2–4 秒召回时延（与 worker 启动并行）。
- 去掉“其他会话最近消息”后，跨会话的连续性只依赖核心记忆、召回和检索；用户跨会话接着说时，
  模型需要主动检索。
- 核心记忆按补丁更新，长期可能积累过时条目；靠上限淘汰和用户编辑纠正。
- 工作笔记按会话拆分后，一个会话里记下的约束不会自动带到另一个会话；需要长期生效的规则应进核心记忆。
- 提取收紧后记忆条目会变少，偶尔有用的过程细节只能从原文和段落档案检索。
