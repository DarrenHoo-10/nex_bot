# 长会话上下文与记忆：技术方案

状态：已实现（分支 `claude/stoic-rubin-0b1920`，2026-10-28），尚未合并和部署。
验证记录：[长会话上下文与记忆](../verification/long-context-memory.md)。

实现与方案的差异：

- P0.4 在校准触发之外保留“原始估算 ≥ 窗口 90%”的兜底触发，避免低校准系数让会话卡死。
- P3 的维护记录在独立的 `maintenance_runs` 表，而不是 `task_runs.kind`（后者带有指向 `tasks` 的非空外键）。
- P4 的段落只在用户下一条消息到达时关闭；后台维护不关闭段落。“新话题”在任务进行中拒绝。
- P1 的“工作上下文”和 P4 的“新话题”已加到 Web 与 Mac/iOS；Android 尚未加。

## 1. 目标与不变的原则

个人助手的连续性应当靠**记忆和可检索的原文**，而不是一条无限增长的模型上下文。

保留现有设计中已经正确的部分：

- 原文只追加、永不删除；所有缩减都是投影上的 `context_edit` / `compaction` 记录，
  原文可用 `memory.search(query="entry:<id>")` 取回。
- 摘要不完整就不替换（`finish_reason!=='stop'` 时保留原文）。
- 工具调用与结果成对，切分只发生在用户轮次边界。
- 历史、记忆和工具结果是资料，不是授权。

## 2. 现状与问题（基于 Tokyo 线上数据）

| 现象 | 数据 / 代码 |
|---|---|
| 压缩只在请求超过窗口 80% 时同步触发 | `worker.ts` `transformContext`，阈值 `min(0.8·window, inputBudget)` |
| 50 万窗口要涨到 40 万才压缩 | grok 近 10 天 213 次调用，平均输入 47,910，最大 99,170 Token |
| 前缀缓存几乎不命中 | 同期 grok 输入 10,204,940，缓存读取 629,888（**6%**）。系统提示末尾含毫秒级时间、设备目录和历史索引（`runtime.ts` `systemPrompt` 的 `<system-reminder>`），每次请求都变，而系统提示位于全部历史之前 |
| 大工具结果长期驻留 | 会话 `b9568ec9`：10 个结果共 134 万估算 Token，在投影中留存 7 天 |
| 每轮把系统提示追加进投影 | `worker.ts:88` 每次启动 `appendMessage(system)`；同一投影累计 61.5 万估算 Token 的过期系统提示（发送时被 `clean()` 过滤，但存储、加载、IPC 都带着） |
| 投影整块读写 | `projection.ts` 一个 JSON 字段存全部条目，每次 `snapshot` 整体重写（该会话 4.1 MB） |
| 估算偏高 | 中文按 1.5 Token/字；该会话估算 147 万，而折叠时代真实输入不足 10 万 |
| 所有话题混在一条会话 | 打招呼、建文档、生图、截屏、改代码交替出现，间隔数天 |
| 工作笔记靠模型自觉维护 | 提示要求 `memory.write(scope="context")`，Core 不保证更新 |
| 长期记忆只读消息正文 | `assistant-memory.ts` `process` 只处理 `agent_messages` 的 user/assistant/peer 文本，不含工具结果；召回为关键词 FTS + `relevance` |

## 3. 目标架构

模型每次看到的内容分三层：

```text
┌ 稳定前缀（可缓存）────────────────────────────────┐
│ 宪法与能力契约 · 身份 · 长期记忆账本（只追加）      │  变化时才失效
├ 段落上下文（工作上下文）─────────────────────────┤
│ 段落摘要（compaction）· 工作笔记 · 最近完整轮次     │  ≤ 工作预算
├ 易变尾部 ────────────────────────────────────┤
│ 时间 · 设备目录 · 召回记忆 · 当前用户输入          │  每轮重建，放最后
└──────────────────────────────────────────┘
可检索层（不进上下文）：原文条目、段落档案、长期记忆、工具原文分页
```

三个关键转变：

1. **预算固定**：工作上下文有自己的预算，窗口只是上限。
2. **维护前置**：缩减在轮次结束后的空闲时间完成，发消息时通常无需等待。
3. **段落化**：长时间间隔或话题切换时收尾一个段落，把它变成档案和长期记忆。

## 4. 分阶段方案

### P0 计量、缓存与存储（低风险，先做）

**P0.1 易变内容移出系统提示**

- `systemPrompt()` 拆成 `stable`（权限模式到长期记忆）与 `volatile`（时间、设备、
  历史索引、工作笔记）。
- `clean()` 和 `permit.systemPrompt` 只放 `stable`；`volatile` 作为最后一条用户
  消息之前的独立块注入（OpenAI 协议用一条 `user` 角色的 `<system-reminder>`，
  Anthropic 协议拼到末尾用户消息的首个 text part），不写入投影。
- 长期记忆账本已是只追加顺序，保持不变。
- 验收：同一会话连续两轮，第二轮请求体从开头到上一轮最后一条消息逐字节相同；
  线上 `cache_read / input_tokens` 从 6% 显著上升（目标 > 50%，取决于服务商）。

**P0.2 系统提示不再每轮进投影**

- `worker.ts:88` 改为：投影中只保留最近一条系统消息，内容相同则不追加。
- 一次性迁移：加载时丢弃除最后一条以外的旧 `system` 条目（它们从不发送）。

**P0.3 投影分段存储**

- 新表 `projection_entries(runtime_id, seq, entry_id, type, json)`，只追加；
  `projections` 只存头信息。`save` 只写新增条目（条目不可变，`context_edit` 本身是新条目）。
- `load` 先读到最近一次 `compaction` 边界之后的条目，加上被引用的条目；
  `entry:<id>` 检索按 `entry_id` 索引直接查。
- 迁移：首次启动把旧 JSON 拆成行，校验条目数与哈希后再切换。

**P0.4 用量校准**

- 记录每个模型的校准系数 `ratio = EMA(真实 input_tokens / 估算)`，来源是
  `model_invocations` 已有的回执。
- 触发判断用 `上次回执 input + 估算(新增部分) × ratio`；无回执时退回纯估算。
  所有“能否放进窗口”的硬限制仍用保守估算，只有预算触发使用校准值。

### P1 固定工作预算

- `model_limit_overrides` 增加 `context_budget`（可空）。
  默认 `workingBudget = min(64_000, inputBudget)`；用户可在模型设置中调整（标签“工作上下文”，
  不加说明段落）。
- 触发线 `workingBudget`；压缩目标 `0.5 × workingBudget`（滞回，避免每轮都压）。
- 尾部保留预算改为 `0.3 × workingBudget`（当前是 `min(20000, 0.6·window − …)`）。
- 硬上限不变：请求仍不得超过 `inputBudget`，否则走现有报错。
- 取舍：这修改 2026-10-25 “放得下就保留完整结果”的决定；放得下的标准从窗口
  改为工作预算。理由是成本、延迟和长上下文注意力衰减，且原文随时可取回。

### P2 轮末工具结果摘要

- 每轮结束（`nex.settled`）后，**上上一轮及更早**的工具结果中超过 1,500 Token 的，
  逐条生成摘要（`summarizeResult`，现有逻辑），写入 `context_edit`。
  最近一个完成的轮次保持完整，保证“继续比较刚才的列表”这类追问不丢细节。
- 图片：更早轮次中的图片 part 换成 `[图片 attachment:<id>]` 标记，原图保留，需要时重读。
- 当前轮内的工具结果不受影响；轮内压力仍由现有三步处理。
- 摘要结果小于原文才替换（现有规则）。

### P3 后台维护

- 新增 worker 维护模式：`WorkerConfig.mode = 'maintain'`，不带输入，复用
  `transformContext` 中的缩减流水线（P2 摘要 → 分批整段压缩），完成后保存投影并退出。
- 触发：任务结束、会话没有排队输入、校准后的上下文超过 `0.7 × workingBudget`
  或存在待摘要的旧工具结果。延迟 10 秒启动，避免用户连续发消息时空转。
- 并发：维护占用与普通任务相同的会话独占（`task_runs` 记录 `kind='maintain'`）。
  用户新消息到达时中止维护；每一步都是原子追加，中止只会少做，不会留下半成品。
  新任务若仍超预算，走现有同步路径兜底。
- 计费：用 `assistant_usage.purpose='maintain'` 记账，不计入记忆日预算，
  但设单会话每日上限（默认 50 万 Token），超出则只在同步路径压缩。

### P4 段落与记忆

**P4.1 段落边界**

- 边界条件（任一满足）：距上一条用户消息 ≥ 6 小时；用户明确开启新话题（界面“新话题”
  操作或指令）；后续可加便宜模型的话题切换判断。
- 边界处在投影追加一个 `compaction`，内容为极短的“上一段要点”（≤ 300 Token），
  加上未完成事项；新段落从干净的工作上下文开始。原会话、原文和检索都不变。

**P4.2 段落档案**

- 新表 `conversation_episodes(id, bot_id, conversation_id, first_entry, last_entry,
  started_at, ended_at, title, summary, open_items, refs_json, tokens)`。
- 收尾时生成结构化档案：标题、主题、决定及原因、工具操作结果（成功/失败及关键标识）、
  未完成事项、`entry:` 引用。可复用后台维护的最后一次压缩结果，不额外调用模型。
- 档案进入 FTS 索引；`memory.search` 增加 `episode:<id>` 展开。

**P4.3 工作笔记由 Core 维护**

- 压缩输出改为结构化 JSON：`{workingNote, history}`。Core 用 `workingNote` 更新
  `assistant_working_notes`（版本号递增），不再依赖模型主动调用 `memory.write`。
  模型仍可手动更新，冲突时以版本号为准。

**P4.4 长期记忆来源扩展**

- `retain` 的输入除消息正文外加入段落档案（含工具操作结果）；档案引用其 `entry:`
  原文，现有来源校验机制（`refs` + 哈希）扩展到条目和档案。
- 召回：在当前 FTS + `relevance` 之外，召回最相关的 1–3 个段落档案摘要放入易变尾部。
  语义检索（Tokyo 已有 Hindsight）作为后续选项，不在本方案范围。

### P5 整理模型

- 压缩、工具摘要、段落档案统一使用“整理模型”：默认沿用记忆设置中的模型
  （`assistant_memory_settings.model`），为空时用对话模型。
- 整理请求的窗口检查使用整理模型自身的上限（`modelLimitSettings`），分批预算也按它计算。

## 6. 实施顺序与验证

| 阶段 | 依赖 | 主要验证 |
|---|---|---|
| P0.1 / P0.2 | 无 | 请求前缀逐字节稳定；线上缓存命中率；投影体积 |
| P0.3 / P0.4 | 无 | 迁移前后条目哈希一致；`entry:` 检索；校准误差 |
| P1 | P0.4 | 超预算触发、滞回、硬上限不变；现有 continuity 测试按新预算更新 |
| P2 | P1 | 上一轮结果完整、更早结果为摘要、原文可取回、图片标记 |
| P3 | P2 | 空闲后自动压缩；用户消息中断维护且无半成品；下一轮无等待 |
| P4 | P3 | 6 小时边界、新话题操作、档案生成与检索、工作笔记自动更新、记忆来源校验 |
| P5 | 任意 | 整理模型窗口与分批按其上限计算 |

每个阶段都用隔离 Core、合成模型和真实 worker 验证（参照
`release/deployment-backlog-253829a6/verify.mjs`），并记录到 `docs/verification/`。

上线后观察的指标（已有表即可计算）：每轮真实输入 Token（`model_invocations`）、
缓存命中率、同步压缩次数与耗时、维护调用次数与 Token（`assistant_usage`）、
`entry:` / `episode:` 检索次数（反映摘要是否丢了需要的细节）。

## 7. 风险与取舍

- **摘要丢细节**：最近一轮保持完整；所有摘要带原文引用；检索次数作为质量信号。
- **后台费用**：只在超预算或有旧大结果时运行；有每日上限；可用便宜的整理模型。
- **缓存失效**：P2 的编辑发生在轮次边界，每轮最多让缓存从被编辑处失效一次；
  P0.1 解决了目前每次请求都失效的主因，净效果仍是大幅改善。
- **段落边界误判**：只用时间和显式操作，不做自动话题判断；边界只是加一层摘要，
  原文和检索不变，误判代价低。
- **范围**：本方案不改客户端；只有 P1 的“工作上下文”设置项需要在 Web 与
  Apple 原生设置页同时增加。
